# Phase 05 - Sharing

## Goal

Add hashed share tokens, expiry, atomic download claims, public
metadata/download routes, and revocation. Only the SHA-256 hash of a share
token is stored; the raw token appears exactly once (in the creation response)
and forms the share URL. Passwords stay out of scope until Phase 07.

- Public routes: `GET /api/public/shares/:token`,

## Out of Scope

- QR codes and storage statistics.
- Physical deletion of exhausted burn-after-reading files (Phase 06 cron sets
  `deleted_at` and removes R2 objects in a safety window).
- `/s/:token` SPA page UI (deferred; the API surface is what Phase 05 tests).
- Scheduled expiry cleanup (Phase 06 cron).

## Existing Constraints

- Security tokens use Web Crypto (32 random bytes, base64url); never
  `Math.random()`. D1 stores SHA-256 hashes, never raw tokens.
- Download-count limiting uses a single atomic `UPDATE ... RETURNING` — never
  SELECT-then-UPDATE (plan §30).
- Downloads stream via `buildDownloadResponse` (Phase 04); never buffer.
- Raw share tokens must never be logged, stored in plaintext, or exposed after
  creation.
- Owner routes require `requireAuth` (+ `requireSameOrigin` for writes);
  public routes carry no cookies and expose no internal fields
  (`object_key`, `r2_upload_id`, DB ids).

## Design Decisions (confirmed)

1. **Token model (plan §27).** `POST /api/files/:fileId/shares` generates a
   32-byte base64url token, stores `SHA-256(token)` in `shares.token_hash`, and
   returns the raw token exactly once inside the share URL
   (`${APP_ORIGIN}/s/<raw>`). `GET /api/shares` returns share ids and metadata
   but never raw tokens (they cannot be reconstructed from the hash).
2. **Resolved: range × download counting.** A share download claim is one
   atomic increment per *request* (plan §30). A resumable client issuing
   multiple range requests consumes multiple counts — accepted for MVP and
   documented; the claim happens before streaming, so a 416 does not consume a
   count (invalid ranges never reach the claim because the share row and file
   are resolved first; a valid-range request that then fails mid-stream still
   counts, which is the intended "download started" semantics).
3. **Atomic claim (plan §30).** One `UPDATE shares SET download_count =
   download_count + 1, last_download_at = ? WHERE id = ? AND revoked_at IS
   NULL AND (expires_at IS NULL OR expires_at > ?) AND (max_downloads IS NULL
   OR download_count < max_downloads) RETURNING *`; zero rows → `403
   FORBIDDEN` (expired, revoked, or exhausted share). D1 supports `RETURNING`.
4. **Public metadata never leaks internals.** `GET
   /api/public/shares/:token` returns `{ name, size, mimeType, expiresAt,
   remainingDownloads, passwordRequired: false }` only; `remainingDownloads` is
   `max_downloads - download_count` or `null` when unlimited. Deleted files
   (`files.deleted_at IS NOT NULL`) make the share unresolvable (`404`).
5. **Burn-after-reading is `max_downloads = 1` + a flag.** The flag
   `delete_file_after_exhausted` is stored; physical deletion happens in a
   Phase 06 cron safety window, never inline during streaming.
6. **Revocation is a flag.** `DELETE /api/shares/:id` sets `revoked_at`;
   revoked shares 404/403 immediately. Idempotent `204` for already-revoked;
   `404` for unknown ids.

## API Changes

### `POST /api/files/:fileId/shares` (owner)

Body: `{ "expiresIn": seconds | null, "maxDownloads": number | null,
"deleteFileAfterExhausted": boolean | null }` — all optional; `password`
rejected → `400 VALIDATION_ERROR` this phase. File must exist and not be
deleted → `404`. Creates the share (`expires_at = now + expiresIn`, `null`
when omitted), stores the token hash, and returns
`{ "id", "url", "expiresAt", "maxDownloads", "deleteFileAfterExhausted" }` —
the only response that ever contains the raw token (inside `url`).

### `GET /api/shares` (owner)

Lists the owner's shares with `{ id, fileId, fileName, createdAt, expiresAt,
maxDownloads, downloadCount, revokedAt, deleteFileAfterExhausted }` (no raw
tokens). Cursor-paginated like files (`limit`/`cursor`, newest first).

### `DELETE /api/shares/:id` (owner)

Revokes (`revoked_at = now`, `204`); idempotent for revoked; `404` unknown.

### `GET /api/public/shares/:token`

- Resolves token → hash → share; unknown/revoked/expired, or the file deleted
  → `404 NOT_FOUND` (public routes never reveal which condition).
- `200` with the public metadata shape above.

### `GET /api/public/shares/:token/download`

- Same resolution → `404` on failure.
- Atomic claim → zero rows → `403 FORBIDDEN`.
- Streams via `buildDownloadResponse` with full Range support (206/416), using
  the stored filename/mime (safe `Content-Disposition`).

## Database Changes

New migration (`db/migrations/0003_*.sql`):

```sql
CREATE TABLE `shares` (
  `id` text PRIMARY KEY NOT NULL,
  `file_id` text NOT NULL,
  `token_hash` text NOT NULL,
  `expires_at` integer,
  `max_downloads` integer,
  `download_count` integer DEFAULT 0 NOT NULL,
  `last_download_at` integer,
  `delete_file_after_exhausted` integer DEFAULT 0 NOT NULL,
  `created_at` integer NOT NULL,
  `revoked_at` integer
);
CREATE UNIQUE INDEX `shares_token_hash_unique` ON `shares` (`token_hash`);
CREATE INDEX `idx_shares_expires_at` ON `shares` (`expires_at`);
CREATE INDEX `idx_shares_file_id` ON `shares` (`file_id`);
```

## Tests

Harness: extend `tests/helpers/d1-fake.ts` with `<`/`>` comparisons, column
comparisons (`download_count < max_downloads`), `col = col + N` assignment,
and `RETURNING` support for `UPDATE`; `tests/helpers/test-env.ts` unchanged.

Matrix (maps to plan §56/§69 and acceptance criteria):

1. Unauthenticated owner share routes → `401`; cross-origin writes → `403`.
2. Create share: `200` with `url` containing a raw token; DB stores the hash
   (equals `SHA-256(token)`, never the token); `expires_at`/`max_downloads`
   honored; `password` in body → `400`.
3. Create share for missing/deleted file → `404`.
4. Public metadata: valid token → `200` with public shape (no `object_key`/id);
   unknown/revoked/expired/deleted-file token → `404`.
5. Atomic claim concurrency: `maxDownloads = 1`, fire 5 concurrent downloads →
   exactly one `200`, four `403`; `download_count` ends at 1.
6. `maxDownloads = 3`, sequential downloads → 3 × `200`, 4th → `403`.
7. Expired share (`expires_at` in the past) → metadata `404`, download `403`.
8. Revoked share → metadata `404`, download `403`; revoke idempotent `204`;
   unknown id `404`.
9. Share download streams content (compare bytes) with safe disposition and
   Range support (`206`/`416` on the public route, consuming one claim for a
   valid-range request).
10. Burn-after-reading: `maxDownloads = 1` + `deleteFileAfterExhausted` →
    first download `200`, second `403`; the file row and R2 object are still
    present (Phase 06 cron owns removal).
11. `GET /api/shares` lists shares (no raw tokens) and paginates.
12. Unlimited share (`maxDownloads: null`) downloads repeatedly → always `200`.

## Acceptance Criteria

- Share URL works end-to-end (create → metadata → download → exhausted).
- Exactly one winner under concurrent `maxDownloads = 1` downloads.
- No raw token in D1, logs, or responses after creation.
- All required commands pass.

# 设计决策摘要（中文，供人工 review）

- **Token 模型（方案 §27）**：32B base64url token，D1 只存 SHA-256；raw token 仅出现在创建响应的 `url` 里；`GET /api/shares` 列表无 raw token（哈希不可逆推）。
- **Range × 计数（任务书要求已解决）**：分享下载按**每次请求**原子 +1（方案 §30）；断点续传多段 Range 消耗多次计数——MVP 接受并文档化；非法 Range 在 claim 前就被拦截（不消耗计数），合法 Range 一旦开始流即计数（"下载已开始"语义）。
- **原子 claim**：单条 `UPDATE ... WHERE 有效 AND download_count < max_downloads RETURNING *`，0 行 → 403；**禁止 SELECT 后 UPDATE**。
- **公共元数据最小暴露**：只返回 name/size/mimeType/expiresAt/remainingDownloads/passwordRequired；文件已删除 → 分享整体 404（不区分条件）。
- **阅后即焚**：`maxDownloads=1` 自然耗尽 + 标志字段；物理删除归 Phase 06 cron 安全窗口，绝不在流中删除。
- **撤销**：`revoked_at` 标志位，幂等 204。

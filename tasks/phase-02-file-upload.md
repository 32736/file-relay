# Phase 02 - Small File Upload

## Goal

Implement upload sessions for files up to 32 MiB, streaming single uploads to
private R2, file metadata, listing, and logical deletion. Lay the table and
protocol foundation that Phase 03 (multipart) reuses without implementing
multipart itself.

## Scope

- `files` and `upload_sessions` tables (migration generated by Drizzle).
- Owner-only upload session creation, single streaming upload, listing, detail,
  and logical deletion.
- Reusable `requireSameOrigin` middleware for state-changing routes.
- Input validation (introduce `zod`; the implementation plan §7 lists it as the
  Worker validation stack and later phases add more inputs).
- In-memory R2 fake for tests; streaming body tests.
- Documentation sync (`docs/api.md`, `docs/database.md`).

## Out of Scope

- Multipart upload, part upload, resume, abort of in-flight R2 multiparts
  (Phase 03).
- Streaming/range downloads and share-ready download paths (Phase 04).
- Sharing (Phase 05), scheduled cleanup/physical R2 deletion (Phase 06).
- File preview, storage stats, search UX, batch operations (Phase 07+).
- Front-end upload/list UI. This phase is API-only; the SPA stays as-is from
  Phase 01.
- Media transcoding, hashing a complete large file in the Worker, buffering the
  request body.

## Existing Constraints

- R2 stays private; the Worker is the only authorization boundary; original
  filenames never become R2 object keys.
- Large uploads stream: `BUCKET.put(objectKey, request.body, ...)` — never
  `request.arrayBuffer()`.
- D1 stores metadata and state; timestamps are Unix epoch seconds; IDs use
  `crypto.randomUUID()`.
- Cookie-authenticated state changes validate `Origin`; management routes use
  `requireAuth`.
- Inputs are validated; avoid unindexed full-table scans (cursor-paginated
  listing on `created_at DESC`).

## Design Decisions (confirmed)

1. **Protocol matches the implementation plan (§17).** `POST /api/uploads`
   returns `{ uploadId, mode, chunkSize, totalParts }`. Files ≤ 32 MiB
   (`UPLOAD_CHUNK_SIZE`) get `mode: "single"`, `totalParts: 1`. Requests above
   the chunk size return `413 PAYLOAD_TOO_LARGE` in this phase — multipart is
   not implemented until Phase 03, and this boundary is explicit and honest
   rather than pretending to support large files.
2. **`upload_sessions` is created with the Phase 03-ready shape**
   (`mode`, `r2_upload_id`, `total_parts`, `status` lifecycle) so Phase 03
   only adds behavior, not schema.
3. **Streaming single upload with size verification.** `PUT
   /api/uploads/:id/content` writes `request.body` straight to R2, then
   compares the R2 object size with the declared `total_size`. On mismatch the
   object is deleted and `400 SIZE_MISMATCH` returned. Content-Length is not
   trusted as the only source of truth.
4. **`POST /api/uploads/:id/complete` is implemented idempotently for
   `single`.** A completed session returns `200` with the file record; a
   session in any other terminal/aborted state returns `409`. This establishes
   the endpoint contract that Phase 03's multipart completion builds on.
5. **R2 object keys are `objects/YYYY/MM/<fileId>`** (implementation plan §16),
   where `fileId` is the `files.id` UUID. The original filename lives only in
   `files.original_name` and is never used for keys, SQL, HTML, or response
   headers in this phase.
6. **Origin protection is a middleware.** `requireSameOrigin` (built on Phase
   01's `isSameOrigin`) is applied to every state-changing route
   (`POST`/`PUT`/`DELETE`), including upload session mutation.
7. **Validation via zod.** `zod` is added as a dependency (plan §7) and used to
   parse/validate request bodies; violations return `400 VALIDATION_ERROR`.
   Filenames are sanitized to a bare basename and limited in length; empty
   names are rejected.
8. **Listing is cursor-paginated** (`limit` default 30, max 100; `cursor` is an
   opaque offset token; `created_at DESC`), filters `deleted_at IS NULL`, and
   never returns `object_key`. `q` name filtering is out of scope this phase.
9. **Deletion is logical.** `DELETE /api/files/:id` sets `deleted_at` and the
   file disappears from listings/downloads immediately; R2 object removal is a
   Phase 06 cron responsibility. Deleting an already-deleted file is idempotent
   `204`.
10. **No front-end UI this phase.** The acceptance surface is the API and its
    tests; upload/list UI is deferred to a later phase.

## API Changes

All routes below require owner authentication (`requireAuth`); state-changing
routes additionally require `requireSameOrigin`.

### `POST /api/uploads`

Body: `{ "name": string, "size": number, "type": string | null }`

- Validates with zod: `name` non-empty (≤ 255 chars after basename
  sanitization), `size` integer within `[1, MAX_FILE_SIZE]`, `type` optional
  string (≤ 255 chars).
- Size ≤ chunk size → creates a `single` session; larger → `413
  PAYLOAD_TOO_LARGE` (multipart arrives in Phase 03).
- Creates the `upload_sessions` row (`status = 'created'`); the `files` row is
  created when the content upload succeeds
  (mirroring plan §23), so listings never expose half-uploaded files. The
  object key is `objects/YYYY/MM/<fileId>`.
- `200` → `{ "uploadId", "mode": "single", "chunkSize", "totalParts": 1 }`.

### `PUT /api/uploads/:uploadId/content`

- Streams the raw binary body to R2 (`BUCKET.put(objectKey, request.body, {
  httpMetadata: { contentType } })`).
- Validates session ownership, `status = 'created'`, `mode = 'single'`, not
  expired; violations → `404 NOT_FOUND` / `409 CONFLICT`.
- After the put: compares R2 object size with `total_size`; mismatch → delete
  the R2 object and `400 SIZE_MISMATCH`.
- On success marks the session `completed`, writes the `files` row (`etag`,
  `size`, `created_at`) and returns `200` with
  `{ "id", "name", "size", "etag" }`.

### `GET /api/uploads/:uploadId`

- Returns session state: `{ "status", "mode", "chunkSize", "totalParts" }`
  (the resume surface Phase 03 extends). `404` for unknown/foreign sessions.

### `POST /api/uploads/:uploadId/complete`

- `single` mode: completed → `200` with the file record (idempotent); anything
  else → `409 CONFLICT`.

### `DELETE /api/uploads/:uploadId`

- Marks the session `aborted`. For `single` mode with no R2 object yet this is
  a state change only (multipart abort is Phase 03). `204`.

### `GET /api/files`

- Cursor-paginated listing: `?limit=30&cursor=<token>`; default `limit` 30,
  max 100; `created_at DESC`; `deleted_at IS NULL`.
- Response: `{ "files": [{ "id", "name", "size", "mimeType", "createdAt" }],
  "nextCursor": string | null }`. Never exposes `object_key` or R2 internals.

### `GET /api/files/:id`

- `200` with the same public file shape as the listing item; `404` if missing
  or logically deleted.

### `DELETE /api/files/:id`

- Logical delete: sets `deleted_at` (epoch seconds); `204`; idempotent for
  already-deleted files.

### Error envelope

Phase 00/01 shape extended with: `VALIDATION_ERROR` (400), `PAYLOAD_TOO_LARGE`
(413), `CONFLICT` (409), `SIZE_MISMATCH` (400), `NOT_FOUND` (404), plus the
existing `UNAUTHORIZED` / `FORBIDDEN`.

## Database Changes

New migration (`db/migrations/0001_*.sql`) with two tables, mirroring the
implementation plan §12:

```sql
CREATE TABLE `files` (
  `id` text PRIMARY KEY NOT NULL,
  `object_key` text NOT NULL,
  `original_name` text NOT NULL,
  `mime_type` text,
  `size` integer NOT NULL,
  `etag` text,
  `created_at` integer NOT NULL,
  `expires_at` integer,
  `deleted_at` integer
);
CREATE UNIQUE INDEX `files_object_key_unique` ON `files` (`object_key`);
CREATE INDEX `idx_files_created_at` ON `files` (`created_at` DESC);
CREATE INDEX `idx_files_expires_at` ON `files` (`expires_at`);
CREATE INDEX `idx_files_deleted_at` ON `files` (`deleted_at`);

CREATE TABLE `upload_sessions` (
  `id` text PRIMARY KEY NOT NULL,
  `file_id` text NOT NULL,
  `object_key` text NOT NULL,
  `original_name` text NOT NULL,
  `mime_type` text,
  `total_size` integer NOT NULL,
  `chunk_size` integer NOT NULL,
  `total_parts` integer NOT NULL,
  `mode` text NOT NULL,
  `r2_upload_id` text,
  `status` text NOT NULL,
  `created_at` integer NOT NULL,
  `expires_at` integer NOT NULL,
  `completed_at` integer
);
CREATE UNIQUE INDEX `upload_sessions_object_key_unique` ON `upload_sessions` (`object_key`);
CREATE INDEX `idx_upload_sessions_status` ON `upload_sessions` (`status`);
CREATE INDEX `idx_upload_sessions_expires_at` ON `upload_sessions` (`expires_at`);
```

Notes: `files.object_key` is unique per plan §12; the `upload_sessions` FK to
`files` is represented by `file_id` (D1/SQLite foreign keys are declared with
the table that needs them — Phase 05+ adds `shares` referencing `files`).

## Tests

Harness additions: `tests/helpers/r2-fake.ts` (in-memory bucket with
`put`/`get`/`head`/`delete`; consumes ReadableStream bodies, records
size/etag/contentType) alongside the existing D1 fake.

Matrix (maps to plan §53/§69 "Upload" and the acceptance criteria):

1. Unauthenticated access to every new route → `401`.
2. `POST /api/uploads` validation: empty name, missing size, size 0/negative,
   size > MAX_FILE_SIZE, oversized name → `400`/`413`; no rows created.
3. `POST /api/uploads` (31 MiB) → `200` `mode: single`, `chunkSize`, `totalParts:
   1`; the `files` row appears only after the content upload succeeds.
4. `POST /api/uploads` (33 MiB) → `413` (multipart deferred to Phase 03).
5. `PUT .../content` happy path with a streamed body → `200`; R2 fake holds the
   object under `objects/<year>/<month>/<fileId>` with the declared
   contentType; session `completed`; `files.etag` recorded; `files.size` equals
   stream length.
6. `PUT .../content` with body length ≠ declared size → `400 SIZE_MISMATCH`;
   R2 object removed; session not completed.
7. `PUT .../content` for unknown session → `404`; for a session owned by nobody
   else (foreign) → `404`; for an already-completed session → `409`.
8. Wrong/missing `Origin` on `POST`/`PUT`/`DELETE` → `403`, no state change.
9. `GET /api/uploads/:id` reflects `status`; unknown → `404`.
10. `POST .../complete` idempotent: after completion `200` with the file
    record; second call `200` again; aborted session → `409`.
11. `GET /api/files` returns owner files, filters logically deleted rows, honors
    `limit` and cursor pagination, and never includes `object_key`.
12. `DELETE /api/files/:id` sets `deleted_at`; file disappears from `GET
    /api/files` and `GET /api/files/:id` → `404`; repeat delete → `204`.
13. Streaming rule guard: upload of a 1 KB and a 5 MiB stream both succeed
    without buffering (asserted via R2 fake receiving a stream).

## Acceptance Criteria

- 1 KB / 5 MiB / 31 MiB single uploads upload and persist correctly (plan §53).
- > 32 MiB is rejected with `413` in this phase.
- Owner listing shows only non-deleted files; logical deletion hides files.
- Raw filenames never appear in R2 keys (asserted in tests).
- All required commands pass.

# 设计决策摘要（中文，供人工 review）

- **协议与方案 §17 一致**：`POST /api/uploads` 返回 `{ uploadId, mode, chunkSize, totalParts }`；≤32 MiB → `single`。**>32 MiB 本阶段返回 413**（multipart 留给 Phase 03），边界明确不假装支持大文件。
- **`upload_sessions` 按 Phase 03 就绪形态建全字段**（`mode`/`r2_upload_id`/`total_parts`/状态机），Phase 03 只加行为不加 schema。
- **流式上传 + 实际大小校验**：`BUCKET.put(objectKey, request.body)` 直写 R2（禁止 `arrayBuffer()`）；put 后对比 R2 对象 size 与声明 size，不一致删除对象并 400。
- **R2 key = `objects/YYYY/MM/<fileId>`**（方案 §16），原始文件名永不进 key。
- **Origin 防护做成中间件 `requireSameOrigin`**，所有 POST/PUT/DELETE 管理路由统一挂载（复用 Phase 01 的 `isSameOrigin`）。
- **引入 zod 做输入校验**（方案 §7 技术栈指定），错误信封沿用 `{ error: { code, message } }` 扩展新码。
- **列表游标分页**（limit 默认 30 / 最大 100，created_at DESC，过滤 deleted_at IS NULL），响应永不含 `object_key`。
- **删除为逻辑删除**（`deleted_at`），R2 物理删除留给 Phase 06 cron；重复删除幂等 204。
- **本期纯 API，不做前端 UI**（上传/列表界面推迟到后续阶段），验收面 = API + 测试。
- **complete 端点本期对 single 幂等实现**，为 Phase 03 multipart 建立契约。

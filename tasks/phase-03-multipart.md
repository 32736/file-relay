# Phase 03 - Multipart Upload

## Goal

Add R2 multipart upload for files above the chunk size (32 MiB): multipart
session creation, streamed part uploads with idempotent UPSERT, resume,
retry, abort, and idempotent completion. Phase 02's session shape already
carries the multipart fields; this phase adds behavior, one table, and tests.

## Scope

- `upload_parts` table (migration generated by Drizzle).
- `POST /api/uploads` opens `mode: "multipart"` for files above the chunk size
  (≤ `MAX_FILE_SIZE`), creating the R2 multipart upload eagerly and storing
  `r2_upload_id`.
- `PUT /api/uploads/:id/parts/:partNumber` — streamed part upload with
  validation and UPSERT (idempotent retry).
- `GET /api/uploads/:id` returns completed parts (resume surface).
- `POST /api/uploads/:id/complete` — idempotent multipart completion with
  crash recovery via `BUCKET.head`.
- `DELETE /api/uploads/:id` aborts the R2 multipart and marks the session.
- R2 fake extended with multipart support; upload tests with a reduced
  `UPLOAD_CHUNK_SIZE` so multi-part flows run with small memory.
- Documentation sync (`docs/api.md`, `docs/database.md`).

## Out of Scope

- Streaming/range downloads (Phase 04), sharing (Phase 05), scheduled cleanup
  of timed-out multipart uploads (Phase 06 cron).
- Front-end upload UI (deferred as in Phase 02).
- Client-side hashing of the complete file, media processing, or any buffering
  of a complete part/upload in the Worker.

## Existing Constraints

- R2 stays private; original filenames never become object keys; IDs are
  `crypto.randomUUID()`.
- Every part streams: `multipart.uploadPart(partNumber, request.body)` — never
  `request.arrayBuffer()`.
- R2 multipart: at most 10,000 parts; every part except the last must be at
  least 5 MiB.
- D1 stores hashes and state, never raw tokens; timestamps are epoch seconds.
- State-changing routes validate `Origin`; management routes use `requireAuth`.
- Schema changes go through migrations.

## Design Decisions (confirmed)

1. **Eager R2 multipart creation.** `POST /api/uploads` for `size > chunkSize`
   calls `BUCKET.createMultipartUpload(objectKey, { httpMetadata })` and stores
   the returned `uploadId` in `upload_sessions.r2_upload_id`. The R2 upload id
   is not exposed to the browser; the public `uploadId` is the D1 session id.
2. **Session status machine gains `uploading`.** `created` → `uploading` after
   the first part is stored → `completed` on success; `aborted`/`failed` are
   terminal. Part uploads accept `created` or `uploading`. Phase 02's `single`
   flow is unchanged (`created` → `completed` in one step).
3. **Part validation (plan §21).** `partNumber` must be an integer in
   `[1, totalParts]`. Part body size must be ≤ `chunkSize`; every part except
   the last must additionally be ≥ 5 MiB (R2's floor), enforced from the R2
   object size after the put — the client's declarations are not trusted.
   Violations → `400 VALIDATION_ERROR` / `413`.
4. **Idempotent part UPSERT.** `INSERT OR REPLACE INTO upload_parts
   (upload_session_id, part_number, etag, size, created_at)` so re-uploading a
   part after a network failure overwrites the stale row; the R2 part itself is
   replaced by `uploadPart` on retry.
5. **Completion is atomic-ish and recoverable (plan §23).** `complete` reads
   all parts, verifies `count === totalParts`, orders by `part_number ASC`,
   calls `multipart.complete(parts)`, then writes the `files` row and marks the
   session `completed` in one D1 `batch`. If the R2 completion already happened
   but D1 failed (crash between the two), a retry detects the existing object
   via `BUCKET.head(objectKey)` and only repairs D1 instead of re-completing.
6. **Abort (plan §24).** `DELETE /api/uploads/:id` on a multipart session
   calls `multipart.abort()` (resumed from `r2_upload_id`) and marks the
   session `aborted`. Completed sessions refuse abort with `409`.
7. **Testable chunk size.** Tests run with a small `UPLOAD_CHUNK_SIZE` binding
   (e.g. 1 MiB) so a few-MiB body exercises multiple parts without large
   memory; the real 33 MiB / 200 MiB behavior is covered by a dev smoke test.
8. **Pure API phase.** No front-end changes.

## API Changes

### `POST /api/uploads`

Same body as Phase 02. For `chunkSize < size ≤ MAX_FILE_SIZE`:

- `200` → `{ "uploadId", "mode": "multipart", "chunkSize", "totalParts" }`
  where `totalParts = ceil(size / chunkSize)`; R2 multipart created eagerly.
- Size above `MAX_FILE_SIZE` still → `413`.

### `PUT /api/uploads/:uploadId/parts/:partNumber`

- Auth + Origin required. Session must be owner-owned, `mode: "multipart"`,
  status `created` or `uploading`, not expired → else `404`/`409`.
- `partNumber` out of range → `400 VALIDATION_ERROR`.
- Streams the body to `multipart.uploadPart(partNumber, request.body)`;
  size rules enforced from the R2 object size (delete the part object on
  violation). First part flips the session to `uploading`.
- UPSERTs `upload_parts` → `200 { "partNumber", "etag" }`.

### `GET /api/uploads/:uploadId`

Extends the Phase 02 response for multipart sessions:

```json
{ "status": "uploading", "mode": "multipart", "chunkSize": 33554432,
  "totalParts": 7, "completedParts": [{ "partNumber": 1, "etag": "..." }] }
```

### `POST /api/uploads/:uploadId/complete`

- `multipart`: verify all `totalParts` parts exist → else `409 CONFLICT`;
  order parts ascending; `multipart.complete(parts)`; insert `files` row and
  mark session `completed` (single D1 batch).
- Crash recovery: if the session is `completed` (or the object exists per
  `BUCKET.head`) but the `files` row is missing, repair D1 and return `200`
  with the file record (idempotent).
- `single`: unchanged from Phase 02 (idempotent `200`).

### `DELETE /api/uploads/:uploadId`

- `multipart`: `multipart.abort()`, mark `aborted`, `204` (idempotent).
- Completed → `409`; `single` behavior unchanged.

### Error envelope

Reuses existing codes; adds nothing new unless part validation needs
`413`/`400` distinctions, which reuse `VALIDATION_ERROR` and
`PAYLOAD_TOO_LARGE`.

## Database Changes

New migration (`db/migrations/0002_*.sql`):

```sql
CREATE TABLE `upload_parts` (
  `upload_session_id` text NOT NULL,
  `part_number` integer NOT NULL,
  `etag` text NOT NULL,
  `size` integer NOT NULL,
  `created_at` integer NOT NULL,
  PRIMARY KEY (`upload_session_id`, `part_number`)
);
CREATE INDEX `idx_upload_parts_session` ON `upload_parts` (`upload_session_id`);
```

The `upload_sessions` table already has `r2_upload_id`, `total_parts`, `mode`,
`access_token_hash`, and the full status lifecycle from Phase 02 — no session
schema changes.

## Tests

Harness: extend `tests/helpers/r2-fake.ts` with multipart state
(`createMultipartUpload`, `resumeMultipartUpload`, `uploadPart`, `complete`,
`abort`, `head`). Tests bind `UPLOAD_CHUNK_SIZE` to 5 MiB so a 13 MiB body
splits into 3 parts (5 + 5 + 3 MiB) — the non-final parts still satisfy R2's
5 MiB floor, which is enforced regardless of the configured chunk size.

Matrix (maps to plan §54/§69 and acceptance criteria):

1. Unauthenticated part/complete/abort routes → `401`.
2. `POST /api/uploads` above chunk size → `200` `mode: "multipart"` with the
   right `totalParts`; R2 multipart created; `r2_upload_id` stored; not exposed
   in the response.
3. Upload all parts of a 13 MiB file (3 parts) → `200` per part; `upload_parts`
   rows match part numbers/etags; session `uploading`.
4. Part retry idempotency: re-upload part 2 with different bytes → row UPSERTed
   (single row per part), R2 part replaced.
5. Part validation: `partNumber` 0 and `totalParts + 1` → `400`; part larger
   than `chunkSize` → `400`/`413`; a non-last part below 5 MiB (with the real
   5 MiB floor enforced regardless of the test chunk size) → `400`.
6. `GET /api/uploads/:id` lists `completedParts` after partial upload; resume
   surface correct.
7. `complete` before all parts → `409`; after all parts → `200` with the file
   record; `files` row created with real size/etag; session `completed`.
8. `complete` idempotency: second call → `200`; crash-recovery path: seed a
   `completed` session without a `files` row + object present → complete
   repairs D1 and returns `200` (no duplicate file rows).
9. `DELETE /api/uploads/:id` mid-upload → `204`, R2 abort invoked, session
   `aborted`; repeat → `204`; completed → `409`.
10. Wrong/missing `Origin` on part/complete/abort → `403`, no state change.
11. Expired multipart session rejects new parts → `409`.
12. `single` uploads keep Phase 02 behavior (regression: one happy-path case).

## Acceptance Criteria

- Files above 32 MiB upload via multipart and land in R2 as one object.
- Part retry and complete retry are idempotent; resume lists completed parts.
- No part or complete request buffers the body in the Worker.
- All required commands pass.

# 设计决策摘要（中文，供人工 review）

- **R2 multipart 创建前置到 session 创建时**（方案 §19）：`POST /api/uploads` 对 >32 MiB 文件立即 `createMultipartUpload`，`r2_upload_id` 存库、不暴露给浏览器。
- **状态机增加 `uploading`**：`created → uploading（首个 part）→ completed`；`single` 流程不变（一次到位）。
- **Part 校验（方案 §21）**：partNumber ∈ [1, totalParts]；每片 ≤ chunkSize；**除最后一片外 ≥ 5 MiB**（R2 硬性下限），以 R2 实际对象大小为准，不信客户端声明。
- **UPSERT 幂等**：`INSERT OR REPLACE`，网络失败重传覆盖旧行。
- **Complete 幂等 + 崩溃恢复（方案 §23）**：R2 complete 成功后 D1 失败 → 重试时 `BUCKET.head` 检测对象已存在 → 只补写 D1，不重复 complete。
- **Abort（方案 §24）**：`multipart.abort()` + status=aborted；已完成拒 abort（409）。
- **测试用小 chunk size**（`UPLOAD_CHUNK_SIZE` 绑定 1 MiB）跑多片流程，真实 33/200 MiB 用 dev 冒烟验证。
- **本期纯 API**，前端不动。

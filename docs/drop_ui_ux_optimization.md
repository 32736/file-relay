## 1. 当前界面概览

当前界面已经具备以下基础结构：

- 顶部 Header：左侧 Logo + `Drop`，右侧文件数量与已用容量
- 顶部 Tab：文件、分享
- 文件上传区域：拖拽上传、选择文件、单文件最大 2 GB
- 文件列表区域：搜索、批量选择、删除选中、文件名、大小、时间
- 页脚：`Drop · drop.28207.cc`

整体风格已经比较干净，但目前更接近“功能原型”，主要问题集中在：

1. 页面横向空间利用不足
2. 上传区占比过大
3. 文件列表存在感不足
4. 操作入口不够明确
5. 视觉层级不够成熟
6. 上传、文件管理、分享之间缺少连续工作流
7. 交互反馈不足
8. 文件分享能力还没有形成产品特色

---

## 2. 产品设计目标

Drop 不应设计成传统“网盘”，也不需要堆叠复杂功能。

更合适的定位是：

> **一个极简、快速、临时、跨设备的文件中转站。**

核心体验：

```text
上传
  ↓
文件出现
  ↓
下载 / 分享 / 复制链接
  ↓
过期 / 删除
```

设计原则：

- 少页面
- 少弹窗
- 少配置
- 强反馈
- 强拖拽
- 强快捷操作
- 分享流程尽量短
- 默认值合理
- 高频操作尽量在当前页面完成

## 3. 页面整体布局优化

### 3.1 增大主内容宽度

当前主内容区域偏窄，在 1920px 屏幕下左右留白过大。

建议：

```css
.page-container {
  width: 100%;
  max-width: 960px;
  margin: 0 auto;
  padding: 0 24px;
}
```

如果未来文件字段较多，可提高到：

```css
max-width: 1040px;
```

推荐范围：

```text
桌面端：960px ~ 1040px
平板：100% - 48px
手机：100% - 32px
```

### 3.2 主模块统一宽度

以下元素应使用同一内容宽度：

- Tab
- 上传区域
- 搜索栏
- 批量操作区
- 文件列表
- 分享列表

避免上传框、搜索栏、表格彼此宽度不一致。

## 5. Header 优化

### 5.1 Logo 与产品名称

当前 `图标 + Drop` 的方向可以保留。

Logo 可继续围绕：

```text
文件 / 数据
    ↓
进入
    ↓
中转站
```

例如：

```text
● ───→ □
```

强调“Drop / 投递 / 进入”的概念。

### 5.2 容量信息

当前：

```text
1 个文件 · 已用 1.7 MB
```

建议：

```text
1 个文件 · 1.7 MB / 10 GB
```

或者：

```text
Storage  1.7 MB / 10 GB
```

可加入极轻量容量条，但不要做成复杂 Dashboard。


### 7.2 推荐上传文案

```text

```

### 7.3 拖拽状态

```text
┌ - - - - - - - - - - - ┐
      把文件拖到这里

```


## 8. 上传进度设计

大文件上传必须有明确反馈：

```text
video.mp4

████████████████░░░░  73%

12.3 MB / 16.8 MB
8.2 MB/s · 剩余约 1 秒

                              ×
```

建议显示：

- 文件名
- 当前大小 / 总大小
- 百分比
- 上传速度
- 剩余时间
- 取消按钮

上传完成：

```text
✓ video.mp4 上传完成
```

上传失败：

```text
! video.mp4 上传失败

网络连接已中断

[重试]
```

## 9. 文件列表优化

文件列表应成为整个应用的核心。

### 9.1 推荐字段

```text
□  名称              大小       上传时间       操作
```

例如：

```text
□  🎬 video.mp4      1.7 MB     2分钟前        ↓  🔗  ⋯
```

### 9.2 显示原始文件名

如果 R2 内部使用：

```text
8e69f8a7cb766b4f4cbc205d879b2851.mp4
```

作为 Object Key，不应该直接展示给用户。

建议数据库保存：

```text
id
object_key
original_name
mime_type
size
created_at
updated_at
```

UI：

```text
旅行视频.mp4
```

R2：

```text
8e69f8a7cb766b4f4cbc205d879b2851.mp4
```

即：

```text
用户看到 original_name
服务端使用 object_key
```

## 14. 分享功能设计

“分享”应成为 Drop 区别于普通 R2 文件管理器的核心能力。

建议支持：

```text

下载次数
访问密码
二维码
阅后即焚
```

### 14.1 创建分享

```text
分享 video.mp4

有效期
[ 24 小时               ▾ ]

下载次数
[ 不限                  ▾ ]

访问密码
[ 可选                   ]

□ 下载后自动销毁

                  [创建分享]
```

### 14.2 分享成功

```text
分享已创建

https://drop.28207.cc/s/7Kx29

[复制链接]    [二维码]
```

```text

```

## 18. Toast 与操作反馈

所有操作都应有快速反馈。

上传：

```text
✓ video.mp4 上传成功
```

删除：

```text
已删除 video.mp4

撤销
```

复制：

```text
✓ 分享链接已复制
```

分享：

```text
✓ 分享链接已创建
```

上传失败：

```text
上传失败，请重试
```

建议 Toast：

- 右下角或右上角
- 2~4 秒自动消失
- 不阻塞主操作

批量：

```text

删除后将无法恢复。

[取消]    [删除 5 个文件]
```

## 43. 总结

当前 Drop 的基础视觉方向无需推翻。

建议继续保持：

```text
极简
轻量
低装饰
开发者工具感
黑白灰主体
紫蓝 Accent
```

重点优化：

```text
页面宽度
  ↓
上传区比例
  ↓
文件列表层级
  ↓
原始文件名
  ↓
文件快捷操作
  ↓
上传状态反馈
  ↓
分享能力
  ↓
二维码
  ↓
Ctrl + V
```

最重要的一条设计原则：

> **不要把“上传区”和“文件列表”做成两个互不相关的模块，而是把整个页面设计成一个连续的文件中转工作流。**

最终希望 Drop 给人的感觉不是：

> “一个 R2 文件管理页面”

而是：

> **“打开、拖进去、拿走——就这么简单。”**
